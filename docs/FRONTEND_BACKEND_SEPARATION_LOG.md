## Intended architecture

Keep one Git repository (a monorepo), not a Git submodule. The web UI and API share types, validation, and domain code; a submodule would add version pinning and synchronization work without isolating Cloudflare deployments.

Create an independently deployed Cloudflare Worker for the API and route `https://opencourts.us/api/*` to it. Keep Pages responsible for web assets. The browser and native app continue using the existing `opencourts.us` origin and `/api/...` paths, so the separation does not introduce a second API hostname, cross-origin cookies, or a CORS/auth redesign. Backend Worker releases and frontend Pages releases will have separate build/deploy commands and rollback points.

Production Pages is now static-only. The API Worker imports the existing API
handlers and shared domain logic from `functions/`; these are source modules,
not Production Pages deployment output. The Preview artifact includes only the
small Pages middleware bridge to its isolated API Worker. Keep the shared
handler modules until they are deliberately extracted into a backend package;
deleting them would currently break the Worker adapter and local Pages
development. The release boundary is already enforced at deployment time.

## Why a submodule is not the plan

A submodule separates source history, but Cloudflare Pages would still package the checked-out `functions/` directory with each Pages deployment. It would not create an independent backend deployment or protect Production routes. A dedicated Worker and explicit `/api/*` routing create the actual runtime and release boundary.

## Safety and rollback rules

- Never run `wrangler pages deploy` from the mixed monorepo as a supposed frontend-only publish while root `functions/` is present.
- Never copy secrets into config files, logs, docs, shell history, Git, or chat. Populate Worker secrets through Cloudflare's secure secret interface; verify only names and availability.
- Do not route Production traffic before the Worker bindings, variables, secrets, compatibility date, and environment gates match the last known-good Pages Production deployment.
- Record the active Pages deployment and current route configuration before each switch. Rollback means restoring the previous `/api/*` routing target first; do not alter databases or migrations as part of a code rollback.
- Current rollback: first restore the previous known-good API Worker version while retaining its route. To return traffic to Pages Functions, first restore a reviewed Pages deployment containing those Functions, then remove the Worker route and reconcile the Wrangler config. The current Production Pages artifact is static-only, so removing the route alone would leave `/api/*` without a handler. Do not roll back or modify D1/R2 data.
- No D1 schema/data migration is required for this deployment-boundary change.
- The Production Worker is configured with `workers_dev: false`. Its only public target is `opencourts.us/api/*`; there is no standalone public `workers.dev` endpoint that can bypass the normal same-origin routing path.
